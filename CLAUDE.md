# kids-chores — правила работы

Little Big Deals — PWA-трекер домашних дел для детей. Монорепозиторий на npm workspaces, общая
архитектура — ADR-001 в ветке `research`.

| Папка | Что внутри |
|---|---|
| `apps/web` | PWA: Vue 3 + Quasar + Dexie (IndexedDB), деплой на GitHub Pages из ветки `main` |
| `apps/api` | Бэкенд: NestJS на Fastify, Prisma, Valkey; HTTP API и `outbox-relay` |
| `apps/notifications` | Сервис уведомлений: читает события из Valkey; пока каркас |
| `packages/contracts` | zod-схемы, общие для фронта и сервисов |
| `infra/`, `compose.yaml` | Локальный контур: Postgres, Valkey, сервисы и nginx в контейнерах |

Node — версия из `.nvmrc`, она же в CI.

## Команды

Из корня репозитория:

```
npm run dev        # дев-сервер apps/web
npm run typecheck  # проверка типов во всех пакетах
npm test           # тесты во всех пакетах
npm run build      # проверка типов + сборка во всех пакетах
npm run splash     # перерисовка экранов загрузки из мастер-кадров apps/web/art/splash-*.png
```

Перед коммитом обязателен зелёный `npm run build` — он включает проверку типов.

Весь контур локально — Podman или Docker, один и тот же `compose.yaml` (структура — ADR-005):

```
cp .env.example .env                 # один раз
podman compose up -d --build         # всё приложение на http://localhost:8080
podman compose down -v               # снести вместе с данными
```

Порты на машине задаются в `.env`; Valkey по умолчанию на 6380, потому что 6379 часто занят.

`api` на машине, без контейнера, — против Postgres и Valkey из Compose:

```
podman compose up -d postgres valkey
cp apps/api/.env.example apps/api/.env       # один раз
npm run dev -w apps/api                      # api на http://localhost:3000
API_URL=http://localhost:3000 npm run dev    # PWA на :5173, /v1 уходит в api на машине
npm run test:integration                     # тесты на настоящих Postgres и Valkey
```

Интеграционные тесты — файлы `*.int.test.ts`, `npm test` их не запускает. В CI для них свои
Postgres и Valkey. Vitest собирает бэк через SWC: esbuild не пишет метаданные декораторов, и без
них Nest не находит зависимости.

Иконки в `apps/web/public/` и мастер-кадры экрана загрузки в `apps/web/art/` — рисованные, их не
генерирует ни один скрипт; SVG-исходники лежат рядом в `art/`. `npm run splash` только читает
`art/splash-portrait.png` и `art/splash-landscape.png` и вписывает кадр нужной ориентации в каждый
размер экрана загрузки, поля чёрные. Исключение — портретные размеры iPad: iPadOS в ландшафте
берёт портретную заставку и растягивает её на весь экран, поэтому туда кладётся ландшафтный кадр,
заранее сжатый по горизонтали. В ландшафте он выглядит ровно, в портрете на iPad — сжатым.
Мастер-кадры рендерятся из SVG в WebKit, не `rsvg-convert`: у него другой шрифт подписи.
Пути к иконкам и заставкам в `index.html` пишутся от корня без `/kids-chores/` (`/favicon.ico`):
Vite сам добавляет `base`, а с префиксом в дев-сервере путь удваивается и иконки не грузятся.
Менять иконку — заменить `pwa-512.png`, `pwa-192.png`, `apple-touch-icon.png`, `favicon.ico`
(16, 32 и 48 px), `favicon.png` и `favicon.svg` (копия `art/icon.svg`) руками; менять заставку —
заменить мастер-кадры и перезапустить команду.

## Архитектура

Фронт — Feature-Sliced Design. Карта слоёв и назначение слайсов — в `apps/web/src/README.md`,
читай его перед тем, как добавлять файлы.

Правила, которые нельзя нарушать:

- **Импорт только вниз по слоям:** `app` → `pages` → `widgets` → `features` → `entities` → `shared`.
  Внутри слоя — нельзя.
- **Вход в слайс только через `index.ts`.** Путей вида `entities/child/model/defaults` снаружи нет.
- **Сущности не импортируют друг друга.** Исключение — явные входы `@x` (сейчас их два, оба для
  `entities/wallet`). Понадобился третий — почти наверняка логика принадлежит фиче слоем выше.
- **Новый код кладём в существующий слайс или заводим новый слайс,** а не в «общую» папку.

## Бэкенд

- Модули Nest, контроллеры, сервисы и провайдеры — классы: так устроен NestJS. Это единственное
  исключение из правила про стрелочные функции; всё остальное — стрелки в `const`, как во фронте.
- `src/platform` — общее без предметной логики (настройки, база, Valkey, outbox, логи),
  `src/modules/<модуль>` — предметные модули. Другой модуль импортирует только `index.ts`,
  репозиторий трогает только свои таблицы, `platform` не знает про модули.
- Настройки — только переменные окружения через zod-схему в `platform/config`; без нужных
  переменных сервис не стартует.
- Таблицы и миграции — Prisma в `apps/api/prisma`; клиент генерируется в `src/generated` и в git
  не хранится. Логи — pino без IP и персональных данных.
- npm 11.19+ не запускает install-скрипты пакетов без разрешения. Разрешения — поле
  `allowScripts` в корневом `package.json` с точной версией: обновил Prisma или esbuild — обнови
  и строку там. Fastify закреплён через `overrides` из-за уязвимостей в версии, которую тянет Nest.

## Код

- **TypeScript strict.** `any`, `as any`, `@ts-ignore`, `@ts-expect-error` — нельзя. Единственное
  приведение типа в проекте живёт в `shared/api/db.ts`, там же объяснено почему.
- **Типы выводим из zod-схем** через `z.infer`, руками не дублируем. Валидация стоит только на
  границах: чтение из IndexedDB, импорт JSON, в будущем — ответы API. Внутри слоёв дальше идут
  обычные типы, без повторной проверки.
- **Схемы чтения снисходительны к старым записям.** На устройствах лежат строки, записанные
  прошлыми версиями, миграций схемы там нет. Новое обязательное поле добавляем как опциональное
  в `stored*`-схеме с подстановкой значения, иначе потеряем историю пользователя.
- **Типы — в `types.ts`, константы — в `constants.ts`** того сегмента, к которому относятся
  (`model/types.ts`, `lib/constants.ts`, `ui/types.ts`). В файлах с логикой, в схемах и в
  компонентах `interface`, `type` и константы не объявляем, `z.infer` тоже живёт в `types.ts`.
  Исключения: пропсы и эмиты компонента остаются в `defineProps`/`defineEmits`, ченджлог —
  отдельный файл данных `model/changelog.ts`, словари — файлы данных в `shared/i18n/messages`.
- **Стрелочные функции в `const`**, не `function`-декларации. Инлайновые колбэки — тоже стрелки.
- **Комментариев в коде не пишем.** Единственное исключение — `shared/api/db.ts`. Если код
  требует объяснения, переписываем код или пишем в `apps/web/src/README.md`.
- **Снимки не переписываем.** `completions.points` и `spends.cost` — цена на момент события.
  Правка каталога задач или наград не должна двигать историю.
- **Строки интерфейса — только через словари** `shared/i18n/messages` на русском, английском и
  испанском, в коде текста нет. Ключ — строковый литерал целиком (`t('editTask.title')`), его
  проверяет `keys.test.ts`. У каждого `$q.dialog` подписи кнопок из словаря. Название
  Little Big Deals и данные пользователя не переводим. Всё остальное — по-английски: имена,
  описания тестов (`describe`/`it`), сообщения коммитов.

## Синхронизация

Как устроена — раздел «Синхронизация» в `apps/web/src/README.md`. Что важно при правке кода:

- Новое поле в синхронизируемой таблице (`SYNC_SPECS` в `features/sync/model/constants.ts`)
  уедет на сервер само. Поле только для этого устройства — в `localFields` вида.
- Не переписываем строку синхронизируемой таблицы с новым `updatedAt`, если в ней ничего не
  поменялось: каждая такая запись уходит на сервер и на все устройства семьи.
- id отметки — `completionId(ребёнок, задача, день)`, пресетов — `presetIdentity`; случайный id
  там нельзя, иначе два устройства создадут две записи об одном и том же.

## Версии

Версия одна и та же в трёх местах, менять их надо вместе:

1. корневой `package.json` → `version` (отсюда vite подставляет `__APP_VERSION__` в футер
   бокового меню);
2. `apps/web/src/entities/app-version/model/changelog.ts` → новая запись сверху, с датой и списком
   изменений на трёх языках приложения: `notes.ru`, `notes.en` и `notes.es`. Тип требует все три,
   без перевода проверка типов не пройдёт;
3. текст коммита — с номером версии в скобках.

Без записи в ченджлоге пользователь увидит уведомление «Обновлено до vX», а экран «Что нового»
покажет старое.

## Планы и исследования

Планы, роадмапы и бэклоги живут **только в ветке `research`** (папки `plans/` и `research/`).
В `main` их нет и быть не должно — там только код приложения. Нужен контекст из плана — читаем
из ветки, не копируя файл в рабочую:

```
git show research:research/01-feature-backlog.md
git ls-tree -r research --name-only | grep -E '^(plans|research)/'
```

Новый план или правка существующего — коммитом в `research`, не в рабочую ветку.

## Git

- Работаем в ветке от `main`, PR в `main`. Пуш в `main` запускает деплой на Pages.
- Коммиты в стиле conventional commits, на английском: `feat:`, `fix:`, `refactor:`, `style:`,
  `chore:`, `docs:`. При подъёме версии — номер в скобках в конце заголовка.
- **Теги ставит CI, не человек.** После мержа в `main` воркфлоу `tag.yml` читает версию из
  корневого `package.json` и создаёт аннотированный тег `vX.Y.Z`, если такого ещё нет. Поэтому версию
  достаточно поднять в одном месте, а `git describe` и откат к конкретной сборке работают сами.
- **Релизы тоже ставит CI — только для минорных и мажорных версий.** Если новая версия вида
  `X.Y.0`, тот же `tag.yml` публикует GitHub Release: заметки собирает
  `apps/web/scripts/releaseNotes.mjs`
  из `changelog.ts` — все записи после предыдущей версии `X.Y.0`, только русский текст `notes.ru`.
  Экран «Что нового» в приложении показывает записи на языке пользователя. Патч (`0.2.7` → `0.2.8`) даёт
  только тег. Поэтому запись в ченджлоге обязательна и для патчей: она попадёт в следующий релиз.
