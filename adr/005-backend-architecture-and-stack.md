# ADR-005. Архитектура и стек бэка

**Статус:** заготовка — решение ещё не записано.

## О чём

Доменное ядро — модульный монолит, то, что действительно отделяется, — отдельные сервисы с первого дня. Здесь же стек и контракт API.

## Что отразить

- Почему не дробим по сущностям: домены маленькие, связаны и меняются вместе
- Критерии выделения сервиса: свой характер нагрузки, общение только событиями, независимое масштабирование; «так чище» — не критерий
- Сервисы: `api` (монолит, модули Identity, Family, Children, Tasks, Rewards, Ledger, Settings, Sync, Backup, Meta), `notifications` — отдельно с первого дня (каркас; уведомления позже), `analytics` — по триггеру
- Границы модулей в ядре: общение через публичный интерфейс модуля и события, чужие таблицы не читаем
- **Как сервисы общаются на примере Notifications:** события через outbox и Streams, отложенные задачи BullMQ, клиент — через обратный прокси, сессия из Valkey; своя схема и копия нужных данных из событий; поведение при сбоях
- Стек: NestJS на Fastify, **Prisma** (RLS — SQL-миграциями и обёрткой клиента с транзакцией на запрос), `nestjs-zod`
- Контракт: REST `/v1`, zod-схемы в `packages/contracts`, OpenAPI из схем
