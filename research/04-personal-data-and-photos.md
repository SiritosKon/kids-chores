# 04 — Персональные данные и изображения

Ресерч перед ADR: какие персональные данные (ПДн) есть в приложении, что из них попадает на сервер,
где живут изображения. Юридические обязанности оператора (уведомление РКН, согласия, GDPR) —
отдельный этап, здесь только то, что влияет на архитектуру и код.

**Статус:** ресерч, версия 2 (сентябрь 2026).

## 1. Что из наших данных — ПДн

| Данные | ПДн? | Где живут |
|---|---|---|
| Аккаунт родителя | Да — даже хеш идентификатора провайдера: мы можем сопоставить его с человеком | Сервер: только `HMAC(sub)` (`02`, раздел 6.2) |
| Email, имя, телефон родителя | Да | **Нигде** — не запрашиваем и не храним |
| Имя ребёнка | Да — вместе с аккаунтом родителя | Сервер и устройство |
| История задач, баллов, наград | Да — в связке с ребёнком | Сервер и устройство |
| IP, User-Agent | Скорее да — РКН толкует широко | Не пишем в постоянные логи; для ограничения частоты — в Valkey с коротким сроком |
| Фото ребёнка | Да | **Нигде** — вместо фото набор аватарок (раздел 4) |
| Аватарки из набора, иконки | Нет — одинаковые для всех | Сборка фронта |
| Картинки вариантов наград | Нет — фото товара, а не человека | Хранилище контура + CDN (раздел 5) |

## 2. Принцип: минимум ПДн

Полностью уйти от ПДн не получится: аккаунт, имена детей и история — это ПДн, и оператором мы
остаёмся в любом случае. Поэтому цель — не «ноль», а **минимум**: храним только то, без чего
приложение не работает. Меньше данных — меньше последствий утечки и проще будущие юридические
обязанности.

## 3. Что сервер хранит и в каком виде

**Храним в открытом виде:** имена детей, каталог задач и наград, историю отметок и покупок,
настройки семьи.

Почему не шифруем на устройстве:

- Сервер должен сам работать с этими данными: сливать конфликты по полям (`02`, раздел 7.4),
  проверять данные, в будущем — писать уведомления с именами детей.
- Шифрование на устройстве требует ключа, который семья может потерять вместе с устройством, —
  тогда теряются и данные.
- Оператором мы остаёмся и с шифрованием: для РКН шифротекст, связанный с аккаунтом, — тоже ПДн.

Как защищаем:

- изоляция семей — `family_id` из сессии и защита строк в Postgres (`02`, раздел 8.1);
- шифрование дисков и бэкапов у провайдера;
- логи без ПДн: id вместо имён, без IP и User-Agent;
- данные не выходят из контура (`03`, раздел 2).

**Не храним:** email, имя, телефон и аватар родителя, токены провайдера входа, фото детей.

## 4. Аватарки детей вместо фото

**Решение:** загрузку фото ребёнка убираем. Вместо неё — **набор готовых аватарок**, родитель
выбирает одну в редакторе ребёнка.

- Фото детей нет ни на сервере, ни в хранилище, ни в бэкапах — самый чувствительный вид ПДн
  исключён целиком, без приватных хранилищ, подписанных ссылок и согласий на фото.
- Аватарки — рисованные ассеты в `public/` сборки фронта, как иконки. Одинаковы для всех, не ПДн,
  раздаются вместе с приложением.
- В строке ребёнка вместо `photo` (JPEG) — `avatarId`, ссылка на аватарку из набора.

**Что меняется в приложении:**

- Редактор ребёнка: вместо «Загрузить фото» — сетка аватарок.
- Схема чтения ребёнка остаётся снисходительной: старая строка с `photo` читается, фото
  не показывается и на сервер не отправляется, ребёнок получает аватарку по умолчанию —
  родитель выбирает новую.
- Экспорт и импорт JSON: `photo` больше не выгружается; при импорте старого файла поле
  игнорируется.
- Сжатие фото (`features/edit-child/lib/resizePhoto.ts`) для детей больше не нужно — переезжает в
  `shared/lib` для картинок наград (раздел 6).

## 5. Картинки вариантов наград

Для фичи «Награда с выбором» (бэклог) родитель загружает картинки вариантов — например, наборы
Лего. Это фото товаров, не ПДн.

**Решение:** загрузка в объектное хранилище контура, раздача через CDN.

| Контур | Хранилище | CDN |
|---|---|---|
| EU | Hetzner Object Storage | Cloudflare — фронт уже там (`03`, раздел 7) |
| RU | Yandex Object Storage | Yandex Cloud CDN |

**Как загружаем:**

1. Приложение готовит картинку на устройстве (раздел 6).
2. `api` выдаёт короткую подписанную ссылку на загрузку одного файла в бакет своего контура.
3. Приложение загружает файл напрямую в хранилище, минуя `api`.
4. В строке варианта сохраняется ключ файла; картинка открывается по адресу CDN.

**Правила:**

- Имя файла — случайный id, без имени награды и id семьи. Список файлов бакета закрыт.
- Страницы с картинками не индексируются (`noindex`, закрытый листинг).
- Вариант уходит в архив — картинка остаётся: на неё ссылается история выбора.
- Ограничения на загрузку: только изображения, размер до ~1 МБ после сжатия.
- Картинки из магазина защищены авторским правом. Используем их внутри семьи по случайным ссылкам —
  риск минимальный, но публичной галереи не делаем.

## 6. Обработка изображений на устройстве

- **Перерисовка через canvas** удаляет все метаданные, включая GPS. Ориентацию применяем до
  перерисовки: `createImageBitmap(file, { imageOrientation: 'from-image' })`.
- **Формат — JPEG** (качество ~0,8). Safari не умеет сохранять canvas в WebP и молча отдаёт PNG;
  AVIF умеет только показывать.
- **Размер** — ~1024 px по длинной стороне: в окне выбора варианта картинка крупная.
- Общая функция сжатия живёт в `shared/lib`, размер и качество — параметрами.

## 7. Удаление данных

- **Удалить ребёнка** — из интерфейса, как сейчас: в архив, история сохраняется.
- **Удалить семью** — полное удаление: строки семьи в Postgres и её картинки наград в хранилище.
  Бэкапы очищаются сами по сроку хранения (7–14 дней).
- **Удалить аккаунт** — удаляет `auth_accounts` и сессии; если родитель в семье один — удаляется и
  семья.

## 8. Планы на будущее

- **Фото детей** — если понадобятся, то только зашифрованными на устройстве, с ключом
  восстановления у семьи. Хранилище и CDN видят только шифротекст.
- **Ссылка на товар у варианта** — вместо или вместе с загруженной картинкой.
- **Юридический этап:** уведомление РКН, согласие родителя отдельным документом, политика
  обработки, для EU — представитель по Art. 27 и короткая DPIA (`03`, раздел 10).
