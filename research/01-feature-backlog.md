# 01 — Бэклог фич

Что ещё можно добавить, сгруппировано по **фазам разработки**. Внутри фазы приоритеты: P0 — высокая ценность/скоро, P1 — важно, P2 — приятно. 🆕 — идеи, добавленные при брейншторме (не из первой версии списка).

## Порядок фаз

1. **Фаза 1 — Сейчас (клиент, всё на IndexedDB).** Обкатываем продукт и всю логику локально, без бэка.
2. **Фаза 2 — Бэкенд по архитектуре.** Поднимаем сервисы по `02-backend-architecture.md` (аккаунты, хранилище, брокер, notifications, analytics).
3. **Фаза 3 — Интеграция клиент ↔ бэк.** Подменяем репозитории IndexedDB → API, миграция данных, синк, роли, offline-first.
4. **Фаза 4 — Фичи и улучшения.** То, что имеет смысл только когда всё уже связано (облачный дашборд, Pro, расшаривание).

> **Ключевая предпосылка фазы 1:** дети/задачи/награды/настройки уезжают из констант в IndexedDB (сид из дефолтов). Доступ к данным изолирован в репозиториях (`completionsRepo`, `spendsRepo`, `walletRepo`, `useBalances`), поэтому в фазе 3 подмена IndexedDB → API будет точечной, а UI-редакторы переделывать не придётся.

### Детали: серия + модель наград 🆕

Расширяем награду из «товара за баллы» в сущность с источником и видимостью. Три оси независимы, всё настраивает родитель.

**Награда:**

```js
{
  id, name, icon,
  points,               // цена в баллах
  purchasable: true,    // ось «экономика»: можно купить за баллы
  visibility: 'shop'    // ось «видимость»: 'shop' | 'streak' | 'hidden'
}
```

- `shop` — в общем списке «Награды».
- `streak` — не в общем списке, показывается как приз серии.
- `hidden` — не видна ребёнку, только родителю (сюрприз).

Оси независимы → любые комбинации: обычный товар; только приз серии (`purchasable:false, visibility:'streak'`); **и покупается, и даётся за серию** (`purchasable:true, visibility:'shop'` + привязка к серии); секретная награда (`purchasable:false, visibility:'hidden'`).

**Серия = список milestone'ов** (расширяемо на 3/7/30 дней):

```js
{ id, enabled, days, points: 0, rewardId: null }   // points и rewardId — оба опциональны
```

За серию можно назначить баллы, награду, или и то и другое. `rewardId` ссылается на любую награду, в т.ч. на ту, что параллельно продаётся в shop.

**Выдача (переиспользуем существующее, без новых таблиц):** при достижении серии — (1) если есть `points`, начисляем бонус в леджер; (2) если есть `rewardId`, пишем в `spends` с `cost: 0` и `source: 'streak'`. Награда попадает в историю кошелька, баланс не трогаем. Добавляем только поле `source` в `spends` (`'purchase' | 'streak'`) — чтобы отличать покупку от выданного за серию и корректно откатывать.

**Открытые вопросы (решить до реализации):**

1. **Повторяемость серии:** приз разово или каждый цикл? → сделать настройкой milestone'а (`once` / `repeat`).
2. **Per-child vs общие:** серия/награда общие на всех детей или назначаемые каждому? → начать с общих.
3. **Дни серии при расписании задач:** «день серии» считать только по дням с обязательными задачами (иначе выходные рвут серию) → связывает «Серию» с «Расписанием задач по дням недели».

## Фаза 2 — Бэкенд по архитектуре

Поднимаем сами сервисы (детали — `02-backend-architecture.md`). Пока без привязки к клиенту.

| Сервис / блок | Заметки |
|---|---|
| **Аккаунты + вход (Google/Yandex SSO)** | Идентификация семьи, привязка устройств. |
| **Хранилище (источник правды) + бэкапы** | БД + регулярные резервные копии; не зависеть от локального кеша браузера. |
| **Доменный API** | Награды/задачи/дети/`completions`/`spends` — те же сущности, что в репозиториях клиента. |
| **Серверный баланс + античит** | Единый баланс на всех устройствах, начисления валидируются на сервере. |
| **Notifications-сервис** | Расписания напоминаний per-timezone, шаблоны, push / email / Web Push. Кормится из брокера. |
| **Mail-сервис** | Транзакционная почта (в т.ч. сброс пароля по email). Отдельно или как часть Notifications. |
| **Analytics-сервис + OLAP (ClickHouse)** | Продуктовые/поведенческие события → агрегаты и дашборды. На старте события можно в Postgres. |
| **Брокер/очередь (Redis Streams / BullMQ)** | Асинхрон, развязка сервисов, сглаживание пиков (пользователи в разных TZ). **Не Kafka** — обоснование в `02`. |

## Фаза 3 — Интеграция клиент ↔ бэк

| Фича | Заметки |
|---|---|
| **Подмена репозиториев IndexedDB → API** | Слой доступа уже изолирован — меняем реализацию, UI не трогаем. |
| **Миграция локальных данных в облако** | Импорт существующего IndexedDB в аккаунт при первом входе. |
| **Offline-first + разрешение конфликтов** | Клиент работает оффлайн, синк при сети; правила слияния (last-write-wins/merge по сущности). |
| **Синхронизация между устройствами** | Родитель с телефона, дети с планшета — общий стейт. |
| **Несколько опекунов + роли** | Оба родителя/бабушки в одной семье; роли родитель / со-опекун / ребёнок. |
| **Детский вход (ограниченный экран)** | Отдельный вход ребёнка без доступа к родрежиму. |
| **Сброс пароля по email** | Письмо со ссылкой сброса на почту родителя — теперь есть аккаунты + mail-сервис. |
| **Push-уведомления и напоминания** | «Сделай дела», «неделя закрывается» — серверный планировщик + push-канал, подключённый к клиенту. |
| **Очередь одобрения** | 🆕 Ребёнок отметил задачи → родителю пуш «принять», подтверждение с телефона. |

## Фаза 4 — Фичи и улучшения

Имеют смысл, когда всё уже связано.

| Фича | Заметки |
|---|---|
| **Облачный дашборд родителя (веб)** | Тренды по семье в браузере, а не только в приложении. |
| **Подписка Pro** | Облако/семьи/приватность за деньги (биллинг). |
| **Расшаривание прогресса (read-only)** | 🆕 Ссылка бабушке/дедушке посмотреть успехи ребёнка. |
| **Мультисемья / несколько профилей** | 🆕 Несколько семей на одном аккаунте/устройстве. |
| **Аудит действий родителя** | 🆕 История изменений (кто снял баллы, поменял награду) — прозрачность между опекунами. |
| **Умные напоминания / инсайты** | 🆕 На основе аналитики: «Даниил три дня не читал», лучшее время для напоминаний. |
| **Глубокая геймификация (сервер)** | Ачивки/уровни/сезоны, которые считаются на сервере и переживают переустановку. |
| **Интеграция с календарём** | 🆕 Расписание задач ↔ семейный календарь. |
