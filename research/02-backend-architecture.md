# 02 — Бэкенд: нагрузка, модульный монолит, события, вход, синк

Ресерч перед ADR. По каждому пункту: контекст и ограничения → варианты → решение → риски. Что не
удалось проверить, помечено «не проверено»; оценки помечены как оценки.

**Статус:** ресерч, версия 2 (сентябрь 2026). Решения здесь — предложения для ADR, не финал.

## 1. Зачем бэкенд (драйверы)

1. **Не потерять данные.** Вся история семьи живёт в IndexedDB одного устройства. Её теряют при
   потере, смене или сбросе устройства, удалении иконки или данных сайта, вытеснении при нехватке
   места. Серверная копия и восстановление по входу в аккаунт закрывают эти случаи. Ограничение
   ITP «7 дней без визитов» к установленной PWA не относится — у неё свой счётчик.
2. **Аккаунты и мультисемейность.** Сейчас приложение — «одна семья на устройство». Чтобы им
   пользовались другие семьи, нужны аккаунт, изоляция данных семей и восстановление по входу.
3. **Уведомления (позже).** «Сделай дела», «неделя закрывается» — нужен сервер с расписанием по часовому
   поясу семьи.
4. **Обучение и задел на рост.** Проект — ещё и полигон: событийная архитектура, очереди,
   региональные развёртывания. Часть компонентов закладываем раньше, чем их требует нагрузка
   (см. раздел 5) — это осознанное решение, а не оценка нагрузки.

## 2. Оценка нагрузки

- Семья делает единицы записей в день: отметки задач, редкие покупки наград.
- Амбициозно **10 000 семей**, 10 записей в день на семью → ~100 000 записей/день ≈
  **1–2 записи/с в пике**. Чтения — единицы в секунду (открытие приложения, refetch при фокусе).
- Данные крошечные: годовой леджер семьи — сотни-тысячи строк. Фото — отдельно, см. `04`.
- Всплески — по часовым поясам: крон «напомнить в 18:00 по времени семьи» бьёт волнами.

**Вывод:** один небольшой инстанс API и одна managed-БД держат это с запасом в сотни раз.
Горизонтальное масштабирование по нагрузке не нужно. Всё, что сверх этого, — задел и обучение.

## 3. Форма развёртывания: модульный монолит + выделенные сервисы

**Почему комбинированная схема.** Под нашу задачу и размер приложения отдельные сервисы и
контейнеры под каждую сущность (дети, задачи, награды, леджер) не нужны. Эти домены маленькие,
тесно связаны (отметка задачи → баллы → серия → приз) и меняются вместе — разнесённые по сервисам,
они дали бы распределённые транзакции, сетевые границы и N деплоев без выгоды. Поэтому доменное
ядро — один модульный монолит. А то, что действительно отделяется — другой характер нагрузки,
собственный жизненный цикл, общение только через события, — **выделяем в отдельный сервис сразу**.
Первый такой сервис — Notifications.

**Варианты:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| Микросервисы по доменам | Независимый деплой каждого домена | Домены связаны, транзакции распределённые, N деплоев — накладные расходы без выгоды на нашем масштабе |
| Один монолит на всё | Проще всего | Рассылки и расписания делят процесс с API; границу Notifications потом выделять дороже |
| **Модульный монолит + выделенные сервисы** | Ядро без распределённых транзакций; то, что живёт своей жизнью, изолировано с первого дня | Нужна дисциплина границ модулей в ядре (как FSD на фронте) и контракт событий |

**Решение:**

| Сервис | Что внутри | Когда |
|---|---|---|
| **`api`** — модульный монолит | Все доменные модули (таблица ниже), HTTP API, запись событий в `outbox`, `outbox-relay` отдельной командой из того же образа | С первого дня |
| **`notifications`** — отдельный сервис | Подписки Web Push, расписания напоминаний по часовому поясу семьи, шаблоны, отправка push, лента уведомлений | **Каркас с первого дня** — читает события и пишет их в лог; сами уведомления — позже |
| `analytics` — отдельный сервис | Приём событий, агрегаты, ClickHouse | По триггеру: дашборды или рост объёма событий. До этого события лежат в `outbox` |

**Почему Notifications — отдельно с первого дня:**

- Другой характер нагрузки: волны по часовым поясам («сделай дела в 18:00 по времени семьи»),
  ретраи внешних push-сервисов — не должны тормозить API.
- Не участвует в доменных транзакциях: всё, что ему нужно, приходит событиями (`task.completed`,
  `week.closing`, `family.timezone.changed`).
- Свой жизненный цикл и внешние зависимости (VAPID, Web Push-эндпоинты).
- Отработка событийной архитектуры с настоящим отдельным потребителем (см. раздел 5).

**Границы `notifications`:** свой контейнер и свой образ; своя схема в той же Postgres
(`notifications.*`: подписки, расписания, журнал отправок) — таблицы ядра не читает; с ядром
общается только событиями — consumer group в Valkey Streams и очереди BullMQ. Код — в том же монорепозитории,
общий пакет `contracts` со схемами событий.

**Когда выделять следующий сервис** — только по такому же явному признаку: свой характер нагрузки,
общение только событиями, независимое масштабирование. Размер модуля или «так чище» — не признак.

### Как сервисы общаются: пример Notifications

**Правило:** `api` и `notifications` не вызывают друг друга по HTTP и не читают чужие таблицы.
Всё, что нужно другому сервису, передаётся событием. Клиент ходит только через один адрес API,
а маршрут к нужному контейнеру выбирает обратный прокси.

```mermaid
flowchart TB
  pwa["PWA"]
  proxy["Обратный прокси<br/>Caddy / nginx на VM"]
  api["api"]
  notify["notifications"]
  db_core[("Postgres<br/>схема core + outbox")]
  db_notify[("Postgres<br/>схема notifications")]
  relay["outbox-relay"]
  streams[["Valkey Streams"]]
  bull[["Valkey: BullMQ"]]
  sessions[("Valkey: сессии")]
  push["Web Push"]

  pwa -->|"/v1/*"| proxy
  proxy -->|"/v1/notifications/*"| notify
  proxy -->|остальное| api
  api --> db_core
  db_core --> relay
  relay --> streams
  streams -->|группа notifications| notify
  notify --> db_notify
  notify --> bull
  bull -->|в нужное время| notify
  notify --> push
  api -.->|пишет| sessions
  notify -.->|читает| sessions
```

**Три пути, по которым идут данные:**

1. **От ядра к Notifications — события.** Родитель отметил задачу: `api` в одной транзакции
   пишет отметку и событие `task.completed` в `outbox`, `outbox-relay` перекладывает его в Stream,
   `notifications` читает своей группой потребителей и решает, нужно ли что-то отправить.
   Так же приходят `family.timezone.changed` (перестроить расписания) и
   `device.push_subscribed` (сохранить подписку).
2. **Внутри Notifications — отложенные задачи.** «Напомнить в 18:00 по времени семьи» —
   задача в BullMQ. В нужное время BullMQ отдаёт её обратно `notifications`, тот отправляет
   Web Push и пишет запись в ленту.
3. **От клиента к Notifications — через прокси.** Ленту уведомлений и настройки напоминаний
   клиент читает по `/v1/notifications/*`: прокси отправляет этот путь прямо в `notifications`.
   Сессию `notifications` проверяет сам — читает её из Valkey, куда её положил `api` при входе.

**Что `notifications` хранит у себя:** подписки Web Push, расписания, ленту, журнал отправок —
и копию того, что нужно для текстов и расписаний (часовой пояс семьи, имена детей), собранную
из событий. В таблицы ядра не заглядывает: если ядро поменяет свою схему, `notifications` не
сломается, пока не поменялся формат событий.

**Что при сбое:**

- Упал `notifications` — `api` работает как обычно, события копятся в Stream и будут обработаны
  после перезапуска.
- Упал `outbox-relay` — события копятся в `outbox`, данные не теряются.
- Упал Valkey — `api` пишет данные и события в Postgres; напоминания и новые входы ждут, пока
  Valkey поднимется.

Так же будет общаться и следующий выделенный сервис (Analytics): своя группа потребителей на те
же Streams, своя схема, свой путь в прокси, если понадобится.

### Модули монолита

| Модуль | Что внутри |
|---|---|
| **Identity** | Пользователи, внешние аккаунты (Яндекс, VK, Google) — только хеш идентификатора, сессии, устройства |
| **Family** | Семья как арендатор, часовой пояс, членство. Роль пока одна — родитель |
| **Children** | Дети, фото (ссылка на хранилище, см. `04`), цели |
| **Tasks** | Каталог задач, периоды активности, правило бонуса |
| **Rewards** | Награды, видимость, варианты (см. бэклог «Награда с выбором») |
| **Ledger** | `completions` (+), `spends` (−) со снимками цены, баланс и серии — вычисляются |
| **Settings** | Бонус, вехи серии, прочие правила семьи |
| **Sync** | Приём изменений из очереди устройства, защита от повторов, выдача новых изменений (раздел 7) |
| **Backup** | Экспорт/импорт — тот же JSON-контракт, что сейчас в `features/backup` |
| **Meta** | Версия сервера, `minClientVersion`, ченджлог — `GET /v1/meta` (раздел 9) |

Модули общаются через публичный интерфейс модуля (как `index.ts` слайса на фронте) и через события.
Прямой доступ к таблицам чужого модуля запрещён.

## 5. Брокер и очереди: Valkey с первого дня

**Нагрузки для брокера нет.** На старте хватило бы одного Postgres: очереди (pg-boss, Graphile
Worker), события через таблицу `outbox`, сессии в таблице. Нам нужно на 2–3 порядка меньше, чем
эти инструменты держат.

**Решение: всё равно закладываем брокер с первого дня** — ради масштабирования и чтобы отработать
событийную архитектуру с отдельными потребителями на реальном проекте. Kafka — перебор: отдельный
кластер и операционная сложность без выгоды на нашем объёме.

### 5.1. Почему Valkey, а не Redis

Valkey — форк Redis 7.2.4 в Linux Foundation, тот же протокол и те же команды: Streams, TTL, Lua,
BullMQ работают без изменений.

| | Valkey в контейнере на нашей VM | Redis в контейнере на нашей VM | Managed Redis / Valkey в облаке |
|---|---|---|---|
| Деньги | **Бесплатно** | Бесплатно | ~2,5–3,5 тыс. ₽/мес в Yandex Cloud, от ~€35 в Scaleway |
| Лицензия | **BSD-3, без условий** | С 7.4 — RSAL/SSPL, с 8.0 — ещё и AGPL: бесплатно, но с условиями | Не наша забота |
| Если переедем в managed | Yandex Cloud и OVHcloud предлагают именно Valkey | Не везде | — |

**Итог: Valkey в контейнере на той же VM, что и `api`.** Бесплатно, без лицензионных условий, и
при переезде в managed-сервис ничего не меняется — у российского и европейского облака это тоже
Valkey. Managed-вариант нашей нагрузке не нужен: в Valkey нет данных, которые нельзя восстановить
(раздел 5.4).

### 5.2. Для чего используем

| Задача | Как |
|---|---|
| События между сервисами | **Streams** + consumer groups: у каждого потребителя своя группа и свой темп, подтверждение обработки, повторная выдача зависших сообщений, отдельный поток для сообщений, которые не удалось обработать после N попыток |
| Отложенные и повторяющиеся задачи | **BullMQ**: напоминания по часовому поясу семьи, повторные попытки отправки push |
| Сессии | Ключ `session:{id}` со сроком жизни; список сессий пользователя — для «выйти на всех устройствах» |
| Ограничение частоты запросов | `@nestjs/throttler` с хранилищем в Valkey — работает и при нескольких экземплярах API |

### 5.3. Как событие не теряется

Записать данные в Postgres и событие в Valkey одной транзакцией нельзя. Если упасть между двумя
записями, событие потеряется или появится без данных. Поэтому:

1. `api` пишет событие в таблицу `outbox` в той же транзакции, что и сами данные.
2. `outbox-relay` читает из `outbox` неотправленные события, кладёт их в Stream и помечает
   отправленными.
3. Если процесс упал между «положил в Stream» и «пометил», событие уйдёт ещё раз. Потребители
   помнят обработанные `eventId` и повтор пропускают.

`outbox` заодно — журнал всех событий для Analytics, пока нет ClickHouse.

### 5.4. Как держим Valkey на VM

- Контейнер в том же Docker Compose, наружу не открыт, доступ по паролю.
- Сохранение на диск включено (AOF, запись раз в секунду) — Streams и задачи BullMQ переживают
  перезапуск.
- Лимит памяти и политика `noeviction`: BullMQ требует, чтобы Valkey не выкидывал ключи при
  нехватке памяти.
- Бэкапы не нужны: главная копия данных — Postgres. События лежат в `outbox`, напоминания
  пересоздаются из расписаний семьи, пропавшие сессии — это повторный вход.
- Мониторим длину потоков, отставание потребителей и память.

**Совместимость с Redis держим на случай переезда:** используем только команды, которые есть и в
Redis, и в Valkey (общая база 7.2), модулей Redis 8 (JSON, поиск) не используем. Тогда переезд —
это смена адреса подключения: остановить потребителей, переключить адрес, пересоздать отложенные
задачи из Postgres, запустить.

## 6. Вход и сессии

### 6.1. Контуры и провайдеры

RU и EU — два отдельных сайта (`03`): RU — на российских серверах и российском домене, EU — на
европейских. У каждого свой вход, стандартный для его аудитории, без общих аккаунтов:

| Контур | Провайдер | Протокол | Особенности |
|---|---|---|---|
| **RU** | **Яндекс ID** | OAuth 2.0 Authorization Code + PKCE (S256) | Не OIDC: нет discovery и `id_token`, профиль — `login.yandex.ru/info` |
| **RU** | **VK ID** | OAuth 2.1, PKCE обязателен | `device_id` из колбэка при обмене кода, userinfo только POST |
| **EU** | **Google** | OIDC, Authorization Code + PKCE | Стандартный; минимальный scope — `openid email` |

- RU-контур с входом через Яндекс ID закрывает ч. 10 ст. 8 149-ФЗ: Яндекс ID — информационная
  система российского владельца. Штрафы за нарушение — ст. 13.55 КоАП с 07.07.2026
 .
- EU-контур — иностранный сайт со своим входом, ограничения RU-контура на него не переносим.
- Своих паролей, email-кодов и SMS нет: вход — только через провайдера. Это и проще, и не
  требует хранить контакты (раздел 6.2).
- Sberbank ID, T-ID, Apple — не берём на старте: нужна организация и договоры (Сбер, T-ID), для
  PWA не обязателен и глючит в standalone-режиме (Apple).

### 6.2. Минимум персональных данных при входе

Цель — чтобы сервер знал о родителе как можно меньше. Аккаунт нужен только для одного: узнать ту
же семью на новом устройстве.

- **Запрашиваем минимальный scope.** Google требует `openid` вместе с `email` или `profile` —
  берём `openid email`, email из ответа не сохраняем, берём только `sub`. Яндекс — без
  прав `login:*`: `login.yandex.ru/info` всё равно отдаёт `id`, `login` и `psuid`; `login` сразу
  отбрасываем, ключом берём `psuid` (привязан к приложению — не проверено) или `id`.
- **Храним не идентификатор, а его хеш.** В `auth_accounts` — `provider` + `HMAC(sub, pepper)`,
  где `pepper` — секрет контура. Для входа этого достаточно (сравниваем хеши), а сам
  идентификатор провайдера в базе и бэкапах не лежит.
- **Не храним:** email, имя, телефон, аватар родителя, токены провайдера (после входа не нужны —
  к API провайдера мы больше не ходим).
- **Не логируем IP и User-Agent** в постоянные логи. Rate-limit по IP — только в Valkey с коротким
  TTL.
- **Следствие:** нет канала «написать родителю». Восстановление доступа — только через
  провайдера; уведомления — push и лента в приложении (раздел 11). Email, если понадобится, —
  отдельным согласием и отдельной фичей.

Полностью уйти от ПДн не получится: хеш идентификатора для РКН — тоже ПДн (оператор может
сопоставить), так что оператором в RU-контуре мы остаёмся в любом случае. Минимизация уменьшает
объём и последствия утечки, а не снимает обязанности (`04`).

Что после этого остаётся персональными данными — имена и фото детей, которые вводит родитель, —
разбирается в `04`. Там же — можно ли структурировать хранение так, чтобы сервер вообще не видел
ПДн в открытом виде.

### 6.3. Своё или готовое

| Вариант | Плюсы | Минусы |
|---|---|---|
| Облачный сервис входа (Auth0, Clerk, Supabase Auth) | Ничего не пишем | Нет в обоих регионах, хранит профиль пользователя у себя |
| Свой сервер входа в каждом контуре (Keycloak, Zitadel, Authentik, Ory, Logto) | Готовые сессии, MFA, админка | Ещё один сервис с базой в каждом контуре, хранит профиль пользователя |
| Библиотека Better Auth | Готовые сессии, провайдер VK есть | Рассчитана на пользователя с email; с NestJS — через сторонний пакет |
| **Свой модуль входа** | Храним ровно то, что решили в 6.2 | Сессии и защиту от перебора пишем сами |

**Решение: свой модуль входа (Identity) внутри `api`.**

- Обмен кода на токен у Google — библиотека `openid-client`. У Яндекса и VK протокол нестандартный
  (раздел 6.1), для них пишем по небольшому адаптеру.
- Сами пишем: таблицу `auth_accounts` с хешем идентификатора, сессии в Valkey, ограничение
  попыток входа.
- Кода немного: нет паролей, email и одноразовых кодов — только «вернулся от провайдера → нашли
  или создали аккаунт → выдали сессию».

### 6.4. Сессии

**Решение:** серверная сессия + cookie `httpOnly; Secure; SameSite=Lax`. API на том же сайте, что
и фронт (`app.<домен>` + `api.<домен>` или `/api`). JWT в localStorage не используем.

- httpOnly-cookie не читается скриптом — XSS не уносит сессию.
- Cookie, выставленные сервером, не попадают под 7-дневный лимит ITP (он для cookie из JS); у PWA
  на экране «Домой» свой счётчик. Кросс-сайтовые cookie Safari блокирует — отсюда
  требование «тот же сайт».
- Серверную сессию можно отозвать (выход, потеря устройства) без чёрного списка токенов.
- Сессия живёт **30 дней** и продлевается при каждом использовании: планшет, которым пользуются, не
  разлогинивается, заброшенное устройство теряет сессию через месяц.
- CSRF: `SameSite=Lax` + проверка `Origin` на изменяющих запросах.
- В сессии — только `userId`, `familyId`, `deviceId`, время создания.

**Подвох iOS:** у PWA на экране «Домой» и у Safari **раздельные cookie**. OAuth-редирект может
открыться в Safari, и сессия окажется не в PWA. Решение — передача входа кодом:
если вход завершился в Safari, сервер показывает короткий одноразовый код (живёт минуту), родитель
вводит его в PWA, и PWA получает свою сессию. Сначала проверить на реальном iPad — возможно,
редирект в том же окне остаётся в PWA и код не понадобится.

### 6.5. Родрежим и PIN

Родрежим на общем устройстве остаётся: аккаунт родителя залогинен на семейном планшете, PIN
отделяет «родительские» экраны от ребёнка. Сервер доверяет сессии, PIN — локальный замок.

- Сейчас PIN хранится в `settings` открытым текстом — перед синком хранить хеш (PBKDF2/argon2 с
  солью), иначе он уедет на сервер и в бэкапы.
- Шесть цифр — 10⁶ вариантов: нужен лимит попыток с нарастающей задержкой.
- Сброс PIN — через повторный вход в аккаунт.

## 7. Работа без сети и синхронизация

### 7.1. Как это работает

**Есть сеть — работаем с сервером.** Каждое изменение (отметка задачи, покупка, правка награды)
сразу отправляется на сервер, и только после ответа сервера попадает в локальную базу. Экран
показывает то, что подтвердил сервер. Локальная база (IndexedDB) — кеш последнего состояния.

**Нет сети — работаем с локальными данными.** Приложение продолжает работать как сейчас: изменение
пишется в локальную базу и в **очередь на отправку** — отдельную таблицу в той же базе. В
интерфейсе видно, что сети нет и изменения сохранятся позже.

**Сеть появилась:**

1. Приложение отправляет очередь на сервер по порядку.
2. Сервер применяет изменения по правилам разбора конфликтов (раздел 7.4).
3. Приложение забирает с сервера свежее состояние и перезаписывает кеш — на экране снова то, что
   на сервере.

**Главная копия данных — на сервере.**

### 7.2. Этапы

**Этап 1 — одно устройство (первая версия бэкенда).**

- Первый вход в аккаунт — приложение отправляет на сервер всю локальную базу (в формате
  существующего экспорта JSON).
- Дальше — как в разделе 7.1: онлайн пишем на сервер, офлайн копим очередь.
- Новое или сброшенное устройство — вход в аккаунт, и приложение скачивает всё с сервера.

**Этап 2 — несколько устройств (потом, см. «Планы на будущее»).** Добавляется только одно:
приложение забирает с сервера чужие изменения при открытии и при возврате в приложение, а не только
после выхода из офлайна. Правила разбора конфликтов те же. Мгновенного обновления нет.

### 7.3. Переезд с текущей версии

Локальная база и установленная PWA привязаны к адресу сайта (`siritoskon.github.io`). На новом
домене база будет пустой — данные сами не переедут.

**Для нас это не проблема:** сейчас приложением пользуется одна семья, все данные — на одном
устройстве. Переносим вручную: экспорт JSON на старом адресе → вход на новом → импорт. Отдельный
механизм переноса не делаем. На старом адресе оставляем страницу «Приложение переехало» со
ссылкой.

### 7.4. Конфликты и правила, которые закладываем сразу

Конфликт — это когда очередь из офлайна приезжает на сервер, а там за это время то же самое уже
изменили (на другом устройстве или правкой истории в родрежиме). Политика:

| Ситуация | Итог |
|---|---|
| Офлайн поменяли настройку или запись каталога (цену награды, название задачи), на сервере тоже | **Сливаем по полям.** Поменяли разные поля — сохраняются оба изменения. Одно и то же поле — побеждает то, что пришло на сервер последним. Поэтому клиент отправляет не всю строку, а только изменённые поля |
| Офлайн купили награду, а на сервере баланса уже не хватает | **Покупку принимаем, баланс уходит в минус.** Награда уже выдана в жизни — отменять её задним числом нельзя. Родитель видит пометку о минусе и решает сам: откатить покупку или оставить |
| Одну задачу за один день отметили дважды | **Одна отметка.** Баллы не удваиваются |
| Одна сторона отметила задачу, другая сняла отметку | **Побеждает последнее действие,** пришедшее на сервер |
| Одна сторона удалила (в архив) задачу или награду, другая офлайн её отредактировала или купила | **Правка восстанавливает из архива.** Ничего не теряется; если восстановление не нужно — родитель удаляет ещё раз |

Правила, на которых эта политика держится:

| Правило | Зачем |
|---|---|
| У каждого изменения свой id | Если связь оборвалась и изменение отправилось дважды, сервер узнает повтор и не применит его второй раз |
| Изменение каталога и настроек — набор изменённых полей, а не вся строка | Иначе нельзя слить по полям |
| Сервер нумерует принятые изменения по порядку | «Пришло последним» — это порядок на сервере. Часам устройства не доверяем — на детском планшете они могут уходить |
| Ничего не удаляем, а помечаем удалённым | Правка может восстановить из архива, а другое устройство узнает об удалении. Для задач и наград это уже так (`archivedAt`), для отметок и покупок добавим `deletedAt` |
| id отметки вычисляется из ребёнка, задачи и дня | Две отметки одной задачи за один день — одна строка на сервере |
| День отметки — по часовому поясу семьи | Отметка «за вторник» не должна уехать в среду из-за UTC |
| Баланс и серии не храним, а считаем из истории | Как и сейчас: после слияния истории баланс и серии пересчитываются сами. Минусовой баланс — тоже просто результат подсчёта |
| Сервер отклоняет только некорректные данные | Например, отметку несуществующему ребёнку. Приложение показывает, что именно не прошло |

### 7.5. Почему своя очередь, а не готовая библиотека

Готовые движки синхронизации решают задачу «много пользователей правят одно в реальном времени» —
её у нас нет. А взамен требуют заменить Dexie или держать ещё один сервис.

| Вариант | Почему нет |
|---|---|
| Dexie Cloud | Свой сервер синхронизации: облако или установка у себя от €3 495 |
| RxDB | Пришлось бы уйти с Dexie; часть плагинов платная |
| PowerSync | SQLite вместо Dexie и отдельный сервис. Запасной вариант, если своя очередь не справится с этапом 2 |
| ElectricSQL | Синхронизирует только чтение — отправку всё равно писать самим |
| Zero | Не работает без сети на запись |
| Automerge, Yjs | Для совместного редактирования текста — не наш случай |

**Решение:** своя очередь в Dexie + REST на нашем `api`.

## 8. Мультитенантность и данные

### 8.1. Изоляция семей

- **Первый рубеж:** колонка `family_id` во всех таблицах семьи, скоуп в репозиториях. `family_id`
  берётся только из сессии, никогда из тела запроса.
- **Второй рубеж — Row-Level Security Postgres:** политика
  `family_id = current_setting('app.family_id')::uuid`, в начале транзакции
  `set_config('app.family_id', $1, true)` (флаг `true` — на транзакцию, совместимо с PgBouncer в
  transaction mode). Роль приложения — не владелец таблиц и без `BYPASSRLS`, иначе нужен
  `FORCE ROW LEVEL SECURITY`.
- Ошибка в коде скоупа тогда не превращается в утечку чужой семьи — для данных о детях это важно.

### 8.2. Библиотека для работы с базой (ORM)

ORM — библиотека, через которую код работает с Postgres: в ней описываются таблицы, из этого
описания получаются типы TypeScript, запросы и миграции. Нам от неё нужно три вещи:

1. **Типы из описания таблиц** — чтобы не писать их руками.
2. **Защита строк по семье** (раздел 8.1).
3. **zod-схемы из таблиц** — как на фронте, где типы выводятся из zod.

| ORM | Как описываются таблицы | Защита строк по семье | zod-схемы |
|---|---|---|---|
| **Prisma** | Свой язык схем в файле `.prisma` | Правила — вручную в SQL-миграциях; каждый запрос оборачивается в транзакцию с `family_id` | Генератор из схемы |
| Drizzle | Код на TypeScript, близкий к SQL | Встроена: правила в описании таблицы, попадают в миграции | `drizzle-zod` |
| Kysely | Только построитель запросов; таблицы и миграции — сами | Вручную | Нет |
| TypeORM, MikroORM | Классы с декораторами | Вручную | Нет |

**Решение: Prisma.** Самая распространённая ORM для Node, понятная схема, зрелые миграции.

Что это значит для нас:

- **Защита строк по семье — своими руками.** Правила RLS пишем SQL-миграциями рядом со
  сгенерированными Prisma. Каждый запрос из репозитория идёт через обёртку Prisma Client, которая
  открывает транзакцию и первой командой выставляет `family_id` из сессии. Лишняя транзакция на
  запрос нашей нагрузке не мешает.
- **zod-схемы** — генератором из `schema.prisma`; схемы API в `packages/contracts` остаются
  главными, сгенерированные — для слоя данных.
- **Миграции** — Prisma Migrate: нумерованные, применяются отдельным шагом деплоя.

### 8.3. Таблицы (регион, серверные)

Повторяют текущие таблицы Dexie (`completions`, `spends`, `children`, `tasks`, `rewards`,
`settings`, `streaks`, `versionLog`), плюс аккаунты и служебное.

| Таблица | Назначение |
|---|---|
| `users` | Пользователь региона. Единственная не скоупится по семье |
| `auth_accounts` | Внешние аккаунты: провайдер + внешний id → `userId` |
| `families` | Семья: название, `timezone`, регион |
| `memberships` | `userId` × `familyId` × `role` (пока только `parent`) |
| `devices` | Устройства семьи: для сессий и push-подписок |
| `children`, `tasks`, `rewards`, `reward_variants`, `settings` | Каталог семьи, `archivedAt` вместо удаления |
| `completions` | Отметки: `points` — снимок; уникальность ребёнок × задача × день |
| `spends` | Покупки и призы: `cost` — снимок, `source: purchase \| streak`, выбор варианта |
| `push_subscriptions` | Web Push endpoint + ключи, по устройству |
| `outbox` | События для Streams и журнал для Analytics |
| `processed_mutations` | `mutationId` принятых мутаций (идемпотентность синка) |

У каждой строки семьи: `family_id`, `version`, `createdAt`, `updatedAt`, `deletedAt`/`archivedAt`.
`streaks` на сервер не едет — вычисляется. Фото — в объектном хранилище, в строке только ключ
(см. `04`).

**Инварианты из MVP сохраняются:** `completions.points` и `spends.cost` — цена на момент события;
правка каталога историю не двигает. Выдача приза за серию — строка `spends` с `source: 'streak'`,
отдельной таблицы нет.

## 9. Контракт API, версии и ченджлог

### 9.1. Контракт

Клиент уже выводит типы из zod-схем (`z.infer`), валидация — на границах. Логично сделать zod
единым источником правды и для API.

| Вариант | Итог |
|---|---|
| **REST + zod-схемы в общем пакете + OpenAPI** | **Берём.** `nestjs-zod`: валидация, типы и OpenAPI 3.1 из одних схем |
| ts-rest | Общий контракт клиент/сервер, но поддержка Zod 4 пока в RC |
| tRPC | Не REST: хуже для публичного API, кеширования, других клиентов |

- Общий пакет `contracts` (монорепо): zod-схемы запросов и ответов. Фронт импортирует их напрямую
  в `entities/*/api` — правка там точечная, как и планировалось.
- OpenAPI генерируется из схем — для документации и возможных других клиентов.
- Схемы чтения на фронте остаются снисходительными к старым записям (правило из `CLAUDE.md`).

### 9.2. Версии: что есть сейчас

Сейчас версионируется только фронт:

- версия — `package.json` → `__APP_VERSION__` в шапке приложения;
- ченджлог — `src/entities/app-version/model/changelog.ts`, из него экран «Что нового» и
  уведомление «Обновлено до vX» (по таблице `versionLog` на устройстве);
- тег `vX.Y.Z` ставит CI (`tag.yml`), для `X.Y.0` — GitHub Release с заметками из ченджлога
  (`scripts/releaseNotes.mjs`);
- формат бэкапа — `BACKUP_VERSION = 4` в `features/backup`.

С бэкендом появляются новые вещи, у которых есть версия, и они выходят не одновременно: PWA
обновляется на устройстве лениво (service worker), живёт неделями, а `api` и `notifications`
деплоятся сразу и в два контура.

### 9.3. Одна версия продукта

**Варианты:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Одна версия на весь монорепозиторий** | Как сейчас: один тег, один ченджлог, один релиз; понятно, что с чем совместимо | Бэкенд-правка поднимает версию и фронта (без видимых изменений) |
| Своя версия у каждого пакета (changesets, теги `web@`, `api@`) | Точно видно, что изменилось где | Матрица совместимости, N ченджлогов — для 1–2 разработчиков лишнее |

**Решение: одна версия продукта** — в корневом `package.json` монорепозитория. Фронт, `api` и
`notifications` собираются из одного коммита с одной версией; CI ставит один тег `vX.Y.Z` и, как
сейчас, публикует релиз для `X.Y.0`. Каждый артефакт дополнительно знает свой коммит (`git sha`),
его видно в `GET /v1/meta` и в логах.

Правило семвера для продукта:

- **major** — ломающие изменения для пользователя или для старых клиентов (новая версия API);
- **minor** — новые фичи;
- **patch** — исправления, в том числе чисто серверные.

### 9.4. Совместимость — отдельно от версии продукта

Версия продукта говорит «что вышло». Совместимость держат четыре отдельных контракта:

| Контракт | Как версионируем | Правило |
|---|---|---|
| **HTTP API** | Путь `/v1` | Внутри `v1` — только добавляющие изменения (новые поля и эндпоинты опциональны). Ломающее — `/v2`, `/v1` живёт параллельно до отключения |
| **Клиент ↔ сервер** | Заголовок `X-App-Version` от PWA; `minClientVersion` в конфиге сервера | Клиент старее минимума → `426 Upgrade Required`, PWA показывает «Обновите приложение» и принудительно обновляет service worker. `GET /v1/meta` отдаёт версию сервера и `minClientVersion` |
| **События** (Valkey Streams) | Конверт `{ eventId, type, version, occurredAt, familyId, payload }` | Новые поля — добавляющие. Ломающее — новая `version` события; продюсер какое-то время пишет обе, потребители знают обе. Схемы событий — в `contracts` |
| **Схема БД** | Нумерованные миграции Prisma Migrate | Expand/contract: сначала добавить (колонку, таблицу), выкатить код, потом убрать старое отдельным релизом. Во время деплоя старый и новый `api` работают с одной схемой |

Плюс два формата данных, которые уже есть:

- **Бэкап JSON** — `BACKUP_VERSION`; импорт принимает все старые версии, как и сейчас
  (снисходительные схемы). Это и формат первичной выгрузки на сервер (раздел 7.2).
- **Мутации синка** — у мутации версия схемы; сервер поднимает старые до текущей (upcast),
  а не отклоняет.

Порядок выкатки: миграции → `api` и `notifications` → фронт. Сервер всегда должен понимать
клиентов от `minClientVersion` до текущего.

### 9.5. Один ченджлог на всё приложение

Ченджлог переезжает из `src/entities/app-version/model/changelog.ts` в общий пакет монорепозитория
(данные, не код приложения) и остаётся единственным источником для трёх мест: экран «Что нового»
во фронте, GitHub Release (`releaseNotes.mjs`) и `GET /v1/meta` (версия сервера и что в ней).

Запись описывает версию продукта, а не пакет:

```ts
{
  version: '0.4.0',
  date: '2026-10-15',
  notes: ['Данные сохраняются в аккаунте'],      // для пользователя, на русском — «Что нового»
  internal: ['api: /v1/sync/push', 'миграция 0003'], // только в GitHub Release
}
```

- `notes` — то, что видит пользователь. Может быть пустым у чисто серверного патча — тогда
  уведомление «Обновлено до vX» не показываем.
- `internal` — технические изменения по компонентам (`api:`, `notifications:`, `web:`, `db:`),
  попадают только в релиз на GitHub.
- Запись обязательна для каждой версии, как сейчас: CI падает, если записи нет.

**Контуры.** RU и EU могут стоять на разных версиях (деплой по очереди, откат в одном контуре).
Поэтому версия сервера — всегда из `GET /v1/meta` своего контура, а не из сборки фронта; фронт
показывает обе, если они различаются.

**Что поменяется в правилах репозитория** (при реализации, не сейчас): три места версии из
`CLAUDE.md` сводятся к двум — корневой `package.json` и общий ченджлог; номер версии в тексте
коммита остаётся.

## 10. Стек

| Слой | Выбор | Почему / альтернативы |
|---|---|---|
| Язык | TypeScript strict | Как на фронте |
| Фреймворк | **NestJS** (адаптер Fastify) | Модули, DI, guards, throttler, OpenAPI — структура модульного монолита из коробки. Альтернатива — Hono + `@hono/zod-openapi`: легче, но границы модулей держать дисциплиной. Для обучения и структуры — Nest |
| БД | PostgreSQL (managed) | Источник правды, RLS, PITR |
| ORM | Prisma | Раздел 8.2 |
| Брокер, очереди, сессии | Valkey в контейнере на VM | Раздел 5 |
| Файлы | S3-совместимое хранилище в регионе | Приватное, signed URLs — `04` |
| Auth | Better Auth или свой слой | Раздел 6.3, спайк |
| Push | Web Push + VAPID (`web-push`) | Раздел 11 |
| Контейнеры | Два образа: `api` (+ команда `outbox-relay`) и `notifications` | Раздел 3; оркестрация не нужна — `03` |

## 11. Уведомления

**Не в первой волне.** Сервис `notifications` появляется сразу как каркас: читает события из
Streams своей группой и пишет их в лог — так цепочка событий обкатана до первой настоящей фичи.
Сами уведомления — позже. Что уже известно на тот момент:

- **Web Push на iOS** — с iOS 16.4, только для PWA на экране «Домой», разрешение — по жесту
  пользователя. APNs/FCM напрямую не нужны: стандартный Web Push с VAPID, транспорт выбирает
  браузер (Apple push service, FCM у Chrome и Яндекс Браузера).
- **РФ:** RuStore Push — только для нативных Android-приложений. Web Push в Chrome/Яндекс Браузере
  идёт через FCM, а при мобильных ограничениях («белые списки») FCM бывает недоступен
  — не проверено технически.
- **Вывод:** push — «по возможности», не единственный канал; понадобится лента уведомлений внутри
  приложения. Email не используем: контакты родителя не храним (раздел 6.2).
- Расписания — BullMQ, по часовому поясу семьи; отправка — сервис `notifications`.

## 12. Наблюдаемость и бэкапы

- **Логи:** pino (JSON) в stdout, сбор средствами облака (Yandex Cloud Logging / Loki). Без ПДн
  в логах: id вместо имён.
- **Ошибки:** GlitchTip — совместим с Sentry SDK, лёгкий (от 512 МБ), ставится в каждый регион
 . Self-hosted Sentry — ~16 ГБ RAM и 40+ контейнеров, не берём.
- **Метрики:** OpenTelemetry по желанию; минимум — длина потоков и лаг consumer groups,
  размер outbox, ошибки отправки push.
- **Бэкапы:** managed Postgres с PITR — у Yandex Cloud ежедневный бэкап + WAL, 7 дней по умолчанию,
  срок увеличивается. Плюс регулярный логический дамп вне провайдера (в том же
  регионе) и **проверка восстановления раз в квартал**. Valkey бэкапить не нужно: источник правды —
  Postgres и outbox.

## 14. Риски

| Риск | Что делаем |
|---|---|
| Меняются требования к входу | Провайдеры входа — адаптеры в модуле Identity, новый добавляется без переделки |
| OAuth-редирект уходит в Safari, сессия не в PWA | Передача входа одноразовым кодом; проверка на реальном iPad до ADR |
| Push в РФ не доходит | Лента уведомлений в приложении |
| Valkey на той же VM: упала VM — упал и он | Данных, которые нельзя восстановить, в нём нет; AOF на диске; при росте — managed Valkey |
| Ошибка скоупа → утечка чужой семьи | RLS вторым рубежом, тесты изоляции |
| Старые PWA на устройствах шлют старый формат | `/v1` только с добавляющими изменениями, `minClientVersion` + 426, upcast мутаций (раздел 9.4) |
| Контуры на разных версиях | Версия сервера из `GET /v1/meta` своего контура; expand/contract-миграции |

## 15. Планы на будущее

Не реализуемо на текущем этапе, архитектура оставляет место:

- **Разные устройства и интерфейсы для родителя и ребёнка** — телефон родителя, планшет ребёнка.
  Нужен этап 2 синхронизации (раздел 7.2), роли в `memberships`, возможно разделение клиентов (бэклог,
  «Разделение клиентов»).
- **Вход ребёнка** — без своего аккаунта у провайдера: привязка устройства родителем (QR/код),
  ограниченная роль `child`.
- **Несколько опекунов** — второй родитель, бабушка: инвайты, роли `parent` / `guardian`.
- **Realtime** — SSE или WebSocket через Nest gateway, когда refetch при фокусе станет мало.
- **Analytics + ClickHouse** — отдельная consumer group на Streams.
- **Passkeys** для повторного входа.
- **PowerSync** или аналог — если собственный синк не вытянет мульти-девайс.
