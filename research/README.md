## TL;DR (главные выводы)

1. **Фичи.** Большая часть ближайшего бэклога (редактирование наград/детей/задач, онбординг, настройка бонуса, статистика) **делается локально, без бэка** — можно двигать прямо сейчас на текущей архитектуре, вынеся конфиг из кода в IndexedDB. Бэк нужен только для синка между устройствами, аккаунтов и уведомлений.

2. **Бэкенд.** Реальная нагрузка семейного трекера **крошечная** (десятки-сотни семей, единицы записей в день на семью). **Микросервисы не нужны** — они добавят сложности без пользы. Правильный путь: **модульный монолит** (NestJS) + PostgreSQL + Redis + объектное хранилище, один контейнер, горизонтальное масштабирование при надобности. «Микросервисы» (управление детьми, задачи-кошелёк, уведомления) проектируем как **модули внутри монолита**; выделяем в отдельные сервисы только то, что реально требует независимого масштабирования (кандидаты: воркер уведомлений, аналитика) — и только когда появится причина.

3. **SSO.** Google OIDC — да, но проще взять **managed-auth** (Supabase Auth / Clerk / Auth0 / Firebase). Нюанс: **в RU-сегменте Google-вход может быть недоступен/нестабилен** → в RU основным делаем **Yandex ID / VK ID**, Google — опционально.

4. **Регионы.** RU и EU держим **двумя независимыми развёртываниями** (свои БД, домены, ключи, бэкапы — ничего общего). Это закрывает и 152-ФЗ (локализация ПДн в РФ), и GDPR. Пользователь принадлежит одному региону. Фронт (SPA) регионо-независим — просто указывает на API своего региона.
