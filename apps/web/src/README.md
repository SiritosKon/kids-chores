# Архитектура фронта — Feature-Sliced Design

Правила работы с репозиторием — в `CLAUDE.md` в корне. Здесь — карта: что где лежит.

Слои сверху вниз, импорт разрешён только вниз; внутри слоя — нет.

| Слой | Что лежит | Слайсы |
|---|---|---|
| `app` | Точка сборки: провайдеры (pinia, Quasar), глобальные стили, корневой `App.vue` | — |
| `pages` | Экраны целиком | `home`, `onboarding`, `settings`, `reward`, `task`, `child`, `spends`, `whats-new`, `install` |
| `widgets` | Самостоятельные композиции экрана | `tasks-board`, `goal-meter-board`, `rewards-panel`, `side-menu`, `account-card` |
| `features` | Действия пользователя | `parent-login`, `select-date`, `award-reward`, `rollback-spend`, `wallet-history`, `whats-new`, `backup`, `track-streak`, `celebrate-streak`, `streak-details`, `edit-child`, `edit-task`, `edit-reward`, `edit-settings`, `choose-reward-variant`, `install-app`, `parent-auto-logout`, `starter-presets`, `sign-in`, `passkey-setup`, `pin-question`, `sync` |
| `entities` | Предметные сущности: схема, состояние, доступ к данным | `child`, `task`, `reward`, `completion`, `spend`, `wallet`, `streak`, `settings`, `app-version`, `parent-session`, `account` |
| `shared` | Код без привязки к предметной области | `api`, `lib`, `ui`, `config`, `assets`, `i18n` |

Сегменты внутри слайса: `ui` — вёрстка, `model` — состояние и логика, `api` — доступ к данным,
`lib` — чистые помощники, `config` — настройки. Обязательных нет, берётся нужный.

Типы и константы сегмента лежат рядом с кодом, но отдельными файлами: `types.ts` и
`constants.ts` (`entities/streak/lib/types.ts`, `features/backup/model/constants.ts`). Файл с
логикой или компонент их только импортирует.

## Состояние

Доменное состояние — в `entities/*/model` (`wallet`, `parent-session`), состояние действий —
в `features/*/model` (`select-date`, `edit-child`). Общей папки `stores/` нет намеренно: это
группировка по техническому виду вместо группировки по смыслу.

## Языки

Интерфейс на русском, английском и испанском — `vue-i18n` в `shared/i18n`. Словари лежат в
`shared/i18n/messages`, по файлу на слайс (`editTask.ts`, `homePage.ts`, у сущностей —
`taskEntity.ts`), и в каждом файле три языка рядом. `defineMessages` выводит тип из русского
словаря, поэтому лишний или пропущенный ключ в английском или испанском — ошибка типов. Общие
слова и склонения — в `common.ts`.

В компоненте строки берутся через `useI18n().t`, в модуле без компонента — через
`i18n.global.t`. Ключ пишется только строковым литералом целиком (`'editTask.title'`):
`keys.test.ts` находит такие ключи в коде и проверяет, что они есть в словаре. Склонения —
формы через `|` и `t(key, count)`; для русского три формы, правило на `Intl.PluralRules`
(`russianPlural`). Даты форматирует `dateLocale()`.

Язык хранится в настройках (`settings.locale`). У строк настроек, записанных до 0.5.6, языка нет,
и для них он русский. На новой установке язык берётся с устройства: первый из ru, en, es, иначе
английский. Последний язык ещё и кешируется в `localStorage`, чтобы первый кадр до чтения
IndexedDB шёл на нужном языке. Сменить язык — глобус в футере бокового меню.

Языковой пакет Quasar ставится один раз при запуске: типы `Lang.set` не принимают пакеты из
`quasar/lang`. Поэтому все `$q.dialog` получают подписи кнопок из словаря, а календарь —
названия месяцев и дней через `Intl` (`calendarLocale`, `firstDayOfWeek`).

Название приложения — Little Big Deals, коротко LBD (`APP_NAME`, `APP_SHORT_NAME`), на всех
языках одинаковое и не переводится. Имена детей, задач и наград — данные пользователя, их тоже
не переводим.

## Первый запуск

Пустая база и нет PIN — приложение сразу показывает главную, а поверх неё окно
`OnboardingDialog` (`pages/onboarding`), которое нельзя закрыть: приветствие и PIN дважды. Язык
в окне не спрашиваем — он уже определён по устройству, поменять его можно в меню. При открытии
окна `features/starter-presets` заполняет пустую базу примером на этом языке: ребёнок, три задачи
и три награды из магазина. Серию пример не включает, а бонус за все задачи дня новая установка
получает включённым (`INITIAL_BONUS`, +2 балла). Пресеты создаются, только если детей, задач и наград нет совсем,
поэтому существующие данные не трогаются. Дальше это обычные данные: смена языка их не
переводит. У пресетов постоянные id (`preset-child`, `preset-task-teeth`…) и время создания 0 —
так синхронизация узнаёт нетронутый пример и при входе заменяет его данными семьи.

Без входа приложением пользоваться нельзя: гостя нет. Окно открыто, пока устройство не вошло в
аккаунт или пока нет PIN (`App.vue`, `welcome`), и первым шагом предлагает войти —
`SignInOptions` из `features/sign-in`. Сервер не ответил — вместо кнопок «Нет связи с сервером» и
«Повторить»; появилась сеть — окно спрашивает сервер само. Шаг выводится из состояния аккаунта, а
не хранится: возврат из Google перезагружает страницу, окно снова открывается и, раз вход уже
есть, переходит к PIN; ошибку входа (`?error=` в адресе) показывает плашка над кнопками. После
входа окно сначала ждёт синхронизацию (`sync.run()`) и только потом просит PIN. Вошли в семью,
где уже есть данные, — пример заменён ими, а настройки семьи приехали с `tourPending: false`,
поэтому знакомства не будет. У семьи уже есть PIN — он приезжает в настройках, окно закрывается
само и говорит, что родрежим открывается PIN семьи. Новая семья получает пример и знакомство.
Сессия кончилась на устройстве, где PIN уже есть, — то же окно просит войти снова, а после входа
закрывается.

После PIN включается родрежим и идёт знакомство (`useSetupTour`) — четыре шага по главной: дети,
задачи, награды, меню. Ушли с главной — знакомство встаёт на паузу и продолжается с того же шага
по возвращении. Пока оно идёт, пункт выхода из родрежима скрыт. Крестика у подсказки нет: кнопка
«Пропустить» в подсказке и клик мимо неё спрашивают, пропустить ли знакомство.

## Экраны и маршруты

Экраны переключает `vue-router` с hash-историей (`/#/settings`): на GitHub Pages не нужна
настройка сервера, системная кнопка «Назад» работает. Пути — в `shared/config/constants.ts`,
таблица маршрутов — в `app/router`. Главная живёт в `keep-alive`, чтобы знакомство с
приложением, которое идёт на ней, не сбрасывалось. Настройки и всё внутри них —
отдельные страницы, не модалки (`/settings`, `/settings/stage/:stageId`,
`/settings/stage/:stageId/reward`, `/settings/pin`), и открываются только в родительском
режиме.

Меню — боковая панель слева (`widgets/side-menu`). Если экран шире `DOCKED_MENU_MIN_WIDTH`
(меню и колонка 834 px помещаются рядом), панель закреплена: всегда открыта, название приложения
в ней, кнопки ☰ нет, в шапке только дата. Уже — открывается кнопкой ☰ и ложится поверх экрана.
Шапка в обоих случаях тянется на всю ширину, колонка страницы — по центру оставшегося места.
В меню «Главная», вход в родрежим или его пункты и инструкция по установке;
пункт текущей страницы подсвечен. В футере панели слева глобус с текущим языком — по нажатию
выпадает список языков, справа версия приложения — по нажатию открывается «Что нового».

Направление перехода выставляет роутер по вложенности адреса: глубже — страница выезжает
справа, выше — возвращается слева. Обе страницы на время перехода лежат в одной ячейке сетки
`.page-stack`. Кнопка «Назад» на странице — `useGoBack`: шаг назад по истории, а если истории
нет (страницу открыли по ссылке) — переход на родительский адрес.

Награда тоже правится страницей (`/rewards/:rewardId`, `pages/reward`): форма `RewardEditForm`
одна на главную и на «＋ Новая награда» из этапа, модалки редактора нет. Задача — так же:
`/tasks/:taskId`, `pages/task`, форма `TaskEditForm`; после сохранения страница пересчитывает
серию, потому что правка задачи меняет, какие дни закрыты.

Кошелёк ребёнка — своя страница (`/children/:childId/wallet`, `ChildWalletPage`), на неё ведёт тап
по копилке на главной. В заголовке аватарка и «Кошелёк · имя», ниже баланс и операции по дням
(`WalletHistory`). Править на ней нечего ни ребёнку, ни родителю. Ребёнок правится отдельно:
`/children/:childId` (`ChildPage`, форма `ChildEditForm`), только в родрежиме — тап по имени или
аватарке на главной. Новый ребёнок — `/children/new`.

Остальное, что раньше открывалось окнами, — тоже страницы: серия ребёнка
(`/children/:childId/streak`), история списаний (`/spends`, родрежим), «Что нового»
(`/whats-new`, на неё ведёт и уведомление «Обновлено до vX») и инструкция «Как добавить на экран»
(`/install`). Окнами остаются только короткие шаги внутри действия: вход по PIN и «Забыли PIN?»,
поздравление с этапом серии, выбор варианта подарка и подтверждения «Удалить?».

Черновик этапа живёт в `useStageDraftStore`: со страницы этапа можно уйти создать награду и
вернуться с ней, не потеряв введённое.

## Родительский режим

Выйти из родрежима можно кнопкой рядом с меткой «Родительский контроль» в шапке или пунктом меню;
оба пути спрашивают подтверждение (`useLogout` в `features/parent-login`). Пока идёт знакомство,
кнопки выхода нет.

Родрежим закрывается сам после 5 минут без касаний (`features/parent-auto-logout`). Время
считается от последнего касания, а не таймером в фоне: iOS замораживает таймеры, пока приложение
свёрнуто, поэтому при возвращении на экран проверяем, сколько прошло. Во время знакомства с
приложением автовыход не срабатывает: тур идёт в родрежиме и выйти из него посреди шага нельзя.

PIN хранится хешем: PBKDF2-SHA-256 из WebCrypto, 600 000 итераций, своя соль на каждый хеш
(`entities/settings/lib/secretHash.ts`). Хеш, соль и число итераций лежат в настройках полем
`pinHash`; проверяет и меняет PIN стор настроек (`checkPin`, `changePin`). Открытый PIN прежних
версий (`parentPin`) стор при первом чтении переводит в хеш и стирает. Хеш синхронизируется,
поэтому PIN у семьи один: сменили на одном устройстве — новый приезжает на остальные.

После пяти неверных PIN подряд окно входа делает паузу: 30 секунд, и каждая следующая ошибка
вдвое дольше, но не больше 15 минут (`features/parent-login/lib/pinLock.ts`). Счётчик лежит в
`localStorage` и переживает перезагрузку; верный PIN или сброс его обнуляют.

PIN меняется только через почту, старый PIN для этого не спрашивается. «Сменить PIN» в настройках
и «Забыли PIN?» в окне входа открывают одну и ту же форму `PinResetForm` из
`features/parent-login`: родитель вводит почту, с которой входит через Google, сервер присылает
на неё код из шести цифр, после кода — новый PIN дважды. Из «Забыли PIN?» родитель после этого
сразу попадает в родрежим. Без связи с сервером PIN не сменить.

Сервер почту не хранит: при входе через Google он берёт подтверждённую почту из профиля (право
`email`) и кладёт в `users.email_hash` только её HMAC с `AUTH_PEPPER`, без регистра и пробелов по
краям. Код уходит на тот адрес, который ввёл родитель, и только если его хеш совпал с хешем
аккаунта. Код живёт 10 минут, в Valkey лежит только его HMAC; новый можно запросить раз в минуту,
после пяти неверных кодов нужен новый. Ответы сервера: 422 — не та почта или неверный код, 409 —
сервер ещё не знает почту аккаунта (аккаунт создан до этого и с тех пор не входил через Google),
410 — кода нет или он кончился, 429 — слишком часто. Проверку кода делает сервер, а новый PIN
задаёт само устройство, как и раньше; это защита на уровне MVP. Локально письма ловит Mailpit
из `compose.yaml`: http://localhost:8025. На dev-входе почту можно указать вторым полем.

## Задачи для конкретных детей

Задача без `childIds` — для всех детей, с `childIds` — только для перечисленных. Список детей
лежит в двух местах: у задачи (текущая настройка для формы) и у каждого периода активности (кому
задача была нужна в те дни). Смена детей закрывает текущий период сегодняшним днём и открывает
новый с новым списком (`reassignPeriods`), поэтому правка не двигает прошлые серии. Периоды
прошлых версий записаны без `childIds` и читаются как «для всех».

`isTaskRequiredOn(task, day, childId)` отвечает, нужна ли задача ребёнку в этот день; без
`childId` — нужна ли хоть кому-то. На доске у ребёнка, которому задача не нужна, вместо галочки
прочерк; закрытие дня, бонус и серия считаются по задачам самого ребёнка.

## Квесты

Квест — задача с `quest: true`, которую родитель даёт на несколько дней. Создаётся на той же
странице, что и задача: кнопка «Добавить квест» на доске открывает её сразу в режиме квеста
(`?quest=1`). Срок выбирается из готовых вариантов от сегодняшнего дня или своими датами начала
и конца (`features/edit-task/lib/questTerm.ts`). Срок — единственный период активности, с первого
дня по последний включительно (`questWindow`); квест с будущей датой начала появится на доске в
этот день. После срока квест просто не показывается — «сгорает», в базе ничего не меняется.

Квест не обязательный: `tasksRequiredOn` его пропускает, поэтому он не входит в закрытие дня,
бонус и серию. Выполняется один раз: отметка пишется обычной строкой `completions` за день
выполнения, и в остальные дни срока у этого ребёнка квест показан выполненным
(`getTaskCompletions`). В кошельке баллы за квест — отдельной строкой с его названием.

## Серия

Серия — список этапов в `settings.streak.milestones`: сколько дней подряд и что за это дать.
Этап срабатывает один раз за серию — в день, когда серия становится ровно такой длины. Этап
без `childIds` — для всех детей (так записаны все этапы прошлых версий), с `childIds` — только
для перечисленных; `milestonesFor` отбирает этапы ребёнка для расчёта и окна серии. Правка
этапа закрывает старую версию (`to`) и открывает новую (`from`), прошлые призы не
переписываются. В состоянии серии `hitRule` отмечает, по какому правилу посчитаны поздравления
`celebrated`: записи прошлых версий (`every`, приз каждые N дней) один раз приводятся к числу
срабатываний по новому правилу.

## Сюрприз

Награда «Скрыта — сюрприз» (`visibility: 'hidden'`) не продаётся и не видна в магазине. Если она
приз этапа серии, ребёнок в окне серии видит «Сюрприз» с подарком вместо названия, родитель —
название с пометкой. Название ребёнок узнаёт в поздравлении, когда этап сработает.

## Награда с вариантами

Варианты награды — две таблицы в `entities/reward`: `rewardVariants` (название, порядок, архив)
и `variantPhotos` (фото по id варианта). Фото лежат отдельно, чтобы главная знала, у каких
наград есть варианты, не загружая картинки; фото читаются только в редакторе, окне выбора и
кошельке. Выбор — снимок в строке `spends` (`variantId`, `variantName`, `chosenAt`), как `cost`.

Выбор награды из списка — общий `RewardSelect` в `entities/reward/ui`: иконка, цена, подпись
«где награда» и пункт «＋ Новая награда», который отдаёт событие `create` — куда вести, решает
страница. Пропс `visibilities` отбирает, какие награды подходят: этапу серии — магазин, приз
серии и сюрприз (`PRIZE_VISIBILITIES`), цели — магазин и «только цель» (`GOAL_VISIBILITIES`).

Окно выбора `VariantPickerDialog` лежит в `entities/reward/ui`: им пользуются и выдача за
баллы (`features/award-reward` — выбор до подтверждения), и приз серии
(`features/choose-reward-variant` — выбор после поздравления или по бейджу «Выбери подарок»),
а фичи друг друга не импортируют.

## Цель ребёнка

Цель — ссылка на награду в строке ребёнка: `goal: { rewardId, variantId? }`. Своей цены и
картинки у цели нет — берутся у награды и варианта, поэтому правка награды сразу видна в цели.
Целью может быть награда из магазина или награда «Только цель» (`visibility: 'goal'`): её нет в
магазине и в призах серии, а создать её можно только из карточки ребёнка — «＋ Новая награда» в
поле цели ведёт на `/children/:childId/reward`. Введённое в карточке живёт в `useChildFormStore`
и переживает этот переход, как черновик этапа серии.

На главной в родрежиме под копилкой маленькая кнопка «Добавить цель» (открывает карточку с
раскрытым полем цели, `?goal=1`) и крестик «Убрать цель» с подтверждением. Полоса цели в цвет машинки
ребёнка, «сколько накоплено из цены» (`widgets/goal-meter-board/lib/goal.ts`). Баллов хватает — кнопка
«Получить» запускает обычную выдачу (`useAwardReward`) с уже выбранным вариантом и после выдачи
снимает цель. Награду удалили или убрали в серию или сюрприз — полоса пропадает, строка ребёнка
не трогается.

## Межсущностные связи

Сущность не импортирует сущность. Единственное исключение оформлено через `@x`: папка с файлом
на каждого конкретного потребителя.

```
entities/completion/
  index.ts        публичный API для слоёв выше
  @x/wallet.ts    отдельный вход, открытый лично для entities/wallet
```

Так связь объявлена, а не случилась: открыв `@x`, видно исчерпывающий список зависимых сущностей,
и поверхность доступа узкая. Сейчас таких входов два — `completion/@x/wallet` и `spend/@x/wallet`,
оба потому, что баланс по определению считается по отметкам и списаниям.

## Аккаунт

Запросы к `api` идут через `shared/api/http.ts`: путь от `/v1`, cookie того же адреса, ответ
проверяется схемой из `@kids-chores/contracts`. Сеть упала, сервера нет или ответ не сошёлся со
схемой — функция возвращает `null` или `false`, исключений наружу нет.

`entities/account` при запуске спрашивает `GET /v1/meta` и `GET /v1/me`. Ответ `/me`
запоминается в `localStorage` (`lbd.account`), поэтому без сети приложение открывается сразу, с
последним известным аккаунтом. `401` значит, что сессии больше нет: запись стирается, и окно
первого запуска просит войти; данные на устройстве остаются до входа. Сервер не ответил —
аккаунт остаётся прежним.

Аккаунт создаёт только вход через Google: первый вход заводит пользователя, семью и устройство.
Родитель в семье один, гостя и приглашений нет. Face ID или Touch ID — это passkey: его можно
добавить только уже войдя, поэтому он всегда ведёт в тот же аккаунт. Ключ лежит в Связке ключей
iCloud, так что на другом устройстве с тем же Apple ID вход по Face ID работает без Google.

Способы входа — в `features/sign-in`: Google, Face ID или Touch ID и dev-вход, если сервер его
включил. Google — переход на `/v1/auth/google/start`; после входа сервер возвращает на главную
`#/?signedIn=google`, и `useSignedInNotice` показывает «Вы вошли в аккаунт» и убирает параметр из
адреса. При ошибке сервер возвращает на `#/?error=google`. Сессия живёт в httpOnly-cookie,
скрипт её не видит.

Наверху меню, под названием, между двумя линиями — аватарка и имя; пункт не нажимается.
Строка `SyncStatus` под именем появляется, только когда что-то не так. Отдельной страницы аккаунта нет, править в профиле
нечего: имя и фото берутся из Google. Имя хранится в аккаунте на сервере (`users.name`, до 40
символов), поэтому его видно и после входа по Face ID; каждый вход через Google обновляет его из
профиля (право `profile`), dev-вход пишет имя, под которым вошли. Фото — только на устройстве, в
`localStorage` под ключом с id пользователя; на сервер оно не уходит. После входа через Google
сервер кладёт ссылку на фото профиля в адрес возврата (`&picture=`) и нигде её не хранит.
`useSignedInNotice` убирает её из адреса, а `adoptProviderPhoto` скачивает картинку 256 px; не
скачалась — запоминается сама ссылка. Принимаются только https-ссылки на `googleusercontent.com`.
Где входили только по Face ID, фото нет. `AccountAvatar` показывает фото, без него — первую букву
имени, без имени — значок.

В настройках, в родрежиме, — карточка «Аккаунт» (`widgets/account-card`): аватарка, имя,
`SyncStatus`, переключатель входа по Face ID, «Выйти из аккаунта» и «Удалить аккаунт и все данные».
Переключатель (`features/passkey-setup`) создаёт passkey для открытого аккаунта и запоминает его id
в `localStorage`, чтобы выключить ключ именно этого устройства; вошли на устройстве по Face ID —
переключатель уже включён.

Выход из аккаунта возвращает устройство к первому запуску, чтобы на общем устройстве не
оставалось чужих данных. Карточка сначала отправляет очередь синхронизации. Нет связи с
сервером — выхода нет: httpOnly-cookie скрипт не сотрёт, а с живой сессией данные вернулись бы
после перезапуска. Что-то так и не ушло (сервер отказал) — приложение предупреждает, что эти
изменения пропадут. Потом `signOut` в `entities/account` удаляет сессию на сервере, а
`wipeDevice` — базу IndexedDB целиком, запомненный аккаунт, фото родителей и id passkey из
`localStorage`; язык остаётся. Страница перезагружается на главную, и приложение стартует как в
первый раз. Данные семьи остаются в аккаунте: после входа тем же аккаунтом устройство заберёт их
с сервера.

Удаление аккаунта — `DELETE /v1/me` после подтверждения. Сервер одной транзакцией удаляет
пользователя, его способы входа и passkey, семью со всеми записями и устройствами и её строки в
`outbox`, оставляя одно событие `family.deleted`, потом удаляет сессии всех устройств семьи. Дальше
устройство стирается, как при выходе. Остальные устройства семьи при следующем запросе получают
`401` и показывают вход; войдёте тем же Google — это будет новый аккаунт с пустой семьёй, и
устройство возьмёт её данные вместо старых.

## Синхронизация

Репозитории в `entities/*/api` по-прежнему пишут только в Dexie и о сервере не знают.
Синхронизация — `features/sync` — смотрит на таблицы со стороны и отправляет то, что в них
поменялось. Правила слияния — ADR-004 в ветке `research`.

Синхронизируются дети, задачи, награды, варианты наград, настройки, отметки и покупки. Таблица
Dexie называется так же, как вид записи на сервере (`SYNC_KINDS` в `contracts`). На сервер не
едут фото детей и вариантов наград, открытый PIN прежних версий, флаг знакомства, язык, серии
(`streaks`) и `versionLog`; хеш PIN едет.
Поля, которые остаются на устройстве, перечислены в `localFields` у вида в
`features/sync/model/constants.ts`.

```
запись в Dexie из репозитория
  ↓ событие Dexie storagemutated, через 300 мс
сравнение таблицы с syncShadow — копией того, что ушло на сервер в прошлый раз
  ↓ изменённые поля → syncQueue, новая копия → syncShadow
POST /v1/sync/push по порядку очереди, пачками по 200
  ↓
GET /v1/sync/pull?since=N — чужие изменения в Dexie, N → syncMeta
  ↓
пересчёт серий, доска перечитывает отметки
```

- Время изменения поля — `updatedAt` строки, у покупки — `createdAt` или `chosenAt`. У удаления и
  у настроек — момент, когда синхронизация его заметила. Сервер берёт поле, только если оно не
  старше сохранённого.
- Снятая отметка и откат покупки — изменение `delete`; в Dexie строка удаляется, как раньше.
- id отметки — `ребёнок:задача:день` (`completionId` в `shared/api/ids.ts`): одна задача за день
  на двух устройствах — одна запись, баллы не удваиваются. Старые отметки получили такой id при
  обновлении базы до версии 6. Призы серии — `streak:ребёнок:этап:день`: каждое устройство
  пересчитывает их само и получает те же id.
- Пришедшую запись, у которой в очереди есть неотправленная правка, приложение пропускает: после
  отправки сервер вернёт её уже слитой.

Синхронизация идёт при запуске и входе, через 300 мс после записи в синхронизируемые таблицы,
при возврате в приложение и когда появилась сеть. Сервер не ответил — повтор через 30 секунд.
Пока всё в порядке, про синхронизацию приложение молчит: аккаунт есть всегда, и она просто часть
работы. `SyncStatus` наверху меню и в карточке «Аккаунт» показывает строку, только когда нет связи,
сервер не ответил, сессия кончилась или сервер не принял изменения; в карточке — ещё и сколько
изменений ждёт отправки. Кнопки «Синхронизировать» нет: синхронизация запускается сама.

Первый вход на устройстве:

- на устройстве ничего нет или только нетронутые пресеты первого запуска (id `preset-…`, время
  изменения 0) — приложение берёт данные семьи с сервера, пресеты убирает;
- есть свои данные — они уходят в семью и сливаются с тем, что там уже есть. Детей и задачи,
  заведённые на двух устройствах отдельно, сервер одинаковыми не считает — будут дубли;
- устройство уже было в другой семье — его данные заменяются данными новой семьи, в новую семью
  ничего не уходит: данные прежней остаются на сервере.

Поля из `localFields` приложение берёт только с устройства, даже если они пришли в записи с
сервера: чужое устройство не может поменять язык или флаг знакомства на этом.

Новая таблица, которую надо синхронизировать, — новый вид в `SYNC_KINDS` и запись в `SYNC_SPECS`.
Таблицы на сервере для этого не нужны: записи всех видов лежат в `core.records`.
